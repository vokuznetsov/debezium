# Контракты событий

Avro-схемы сообщений топика `cdc.events` — по одной паре `Key`/`Value` на
таблицу. Это то, на что опирается consumer второй части (Kafka → MS SQL).

Схемы выгружены из Schema Registry с работающего стенда. Как добавить или
обновить контракт — README, раздел 8: там же готовая команда выгрузки.
Актуальный список схем в реестре: `curl -sS http://localhost:8081/subjects`.

Subject в Schema Registry называется `cdc.events-<полное имя Avro-рекорда>`,
например `cdc.events-dbz.catalog.products.Value`. Так работает
`TopicRecordNameStrategy`: у каждой таблицы свой subject, хотя топик один.

## Формат сообщения

Плоский: поля самой строки плюс служебные с префиксом `__`.

| поле | смысл |
|---|---|
| `__op` | `c` — insert, `u` — update, `d` — delete (`r` — snapshot, при `snapshot.mode=no_data` не бывает) |
| `__deleted` | `"true"` у события удаления (`delete.tombstone.handling.mode=rewrite`) |
| `__schema`, `__table` | исходная таблица |
| `__lsn` | позиция в WAL — по ней дедуплицируется приёмник |
| `__txId` | идентификатор транзакции источника |
| `__ts_ms` | время события на источнике |

`before`-образа строки в сообщении нет: для применения в приёмнике достаточно
`after` и первичного ключа. Денежные поля — `bytes` с
`logicalType=decimal` (`decimal.handling.mode=precise`), в JSON-выводе
консьюмера они выглядят как строка байтов, а не как число.

## Как это читать (часть 2, ориентир)

* Топик один, партиция одна — **читатель ровно один**. Consumer group из двух
  участников бессмысленна: второй не получит ничего.
* Consumer не должен знать таблицы заранее: в первых байтах Avro-сообщения
  лежит id схемы, десериализатор сам забирает схему из Schema Registry и
  отдаёт `GenericRecord`. Сгенерированные классы не нужны.
* Кэш подготовленных SQL-выражений — по ключу «id схемы», а не по имени
  таблицы: тогда изменение структуры таблицы автоматически даёт новый ключ.
* Идемпотентность: хранить последний применённый `__lsn` в служебной таблице
  приёмника и писать его **в той же транзакции**, что и данные. При рестарте
  пропускать события с меньшим или равным LSN.
* Порядок коммитов: сначала транзакция в приёмнике, потом ручной коммит
  offset'а в Kafka. Автокоммит запрещён. At-least-once плюс дедупликация по
  LSN даёт эффект exactly-once.
* Foreign key разбирать не нужно: порядок в топике совпадает с порядком в WAL
  источника, родительская строка всегда приходит раньше дочерней.
* DDL-событий Debezium для PostgreSQL не отдаёт — изменение структуры
  таблицы видно как новая версия Avro-схемы. Это стоит как минимум логировать.
