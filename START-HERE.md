# С чего начать

---

## 1. Что вообще делает этот проект

Есть база PostgreSQL — назовём её **(А)**, это источник. Есть база MS SQL —
**(Б)**, это приёмник. Они уже приведены в одинаковое состояние на какой-то
момент времени. Дальше в (А) продолжают идти изменения, и их нужно доставлять
в (Б).

Прямого копирования нет. Между базами стоит Kafka:

```
   (А) PostgreSQL ──▶ Debezium ──▶ Kafka ──▶ ваш consumer ──▶ (Б) MS SQL
       источник       читает WAL   очередь    ЧАСТЬ 2          приёмник
                                              (не сделана)
       └────────── ЧАСТЬ 1: ЭТО И СДЕЛАНО В РЕПОЗИТОРИИ ──────┘
```

**Сделана только левая половина**: изменения из PostgreSQL попадают в Kafka.
Правая половина — программа, которая читает Kafka и пишет в MS SQL — не
делалась, это отдельная задача (часть 2). Для неё в репозитории есть описание
контракта и требований, но кода нет.

Весь проект — это конфигурация: Docker Compose, SQL-скрипты, конфиг
коннектора, shell-скрипты для проверок. Программного кода (Java, Gradle) нет
намеренно.

## 3. Словарь: 12 слов, которые мешают читать

Без них дальше не понять, поэтому по-человечески и коротко.

**WAL** — журнал PostgreSQL. База сначала пишет в него *что именно она
изменила*, потом применяет к данным. Раз в журнале есть все изменения по
порядку — его можно читать и повторять на другой базе. На этом стоит вся
репликация и весь CDC.

**CDC** (Change Data Capture) — «захват изменений». Общее название подхода:
не сравнивать базы, а читать поток изменений.

**LSN** — номер позиции в WAL. Просто счётчик, который всё время растёт.
`LSN = 407 651 328` значит «столько-то байт с начала журнала». Главное
свойство: если у события LSN больше — значит оно произошло позже. Это ваш
единственный надёжный «порядковый номер» события.

**Слот репликации** (replication slot) — закладка в журнале. Пока слот
существует, PostgreSQL не удаляет WAL, до которого этот слот ещё не дочитал.
Именно поэтому можно создать слот сегодня, а читалку запустить завтра —
изменения за это время никуда не денутся. Обратная сторона: если читалка
сломалась и не читает, журнал растёт и однажды кончится диск.

**Публикация** (publication) — список таблиц, изменения которых отдаются
наружу. Всё, что не в публикации, в поток не попадает.

**Debezium** — готовая программа, которая подключается к PostgreSQL как
реплика, читает WAL через слот и превращает каждое изменение строки в
сообщение. Это она делает всю работу части 1. Мы её только настраиваем.

**Kafka Connect** — «хостинг» для таких программ, как Debezium. Debezium —
плагин, Connect — сервис, который его запускает и держит настройки. Общаться с
ним можно по HTTP (поэтому в скриптах есть `curl` на порт 8083).

**Топик и партиция** — топик это очередь сообщений в Kafka; партиция — часть
очереди. Kafka гарантирует порядок сообщений **только внутри одной партиции**.
У нас **один топик `cdc.events` с одной партицией** — именно чтобы порядок был
гарантирован для всех таблиц сразу. Отсюда все остальные ограничения проекта.

**Offset** — номер сообщения в партиции. Читатель хранит «я дочитал до
offset N», чтобы после перезапуска продолжить с того же места.

**Avro** — формат, в котором сообщение записано в Kafka. Бинарный и компактный:
имена полей в каждом сообщении не повторяются, вместо них в начале сообщения
стоит номер схемы.

**Schema Registry** — справочник схем. Debezium регистрирует там описание
каждой таблицы и получает номер; в сообщение попадает только номер. Читатель по
номеру забирает описание и понимает, что за поля внутри. Практический смысл:
**читатель не должен знать 500 таблиц заранее** — он узнаёт структуру из
справочника на ходу.

**Конверт** (envelope) — вот это слово вас и запутало. Debezium по умолчанию
оборачивает изменённую строку в «конверт» со служебной информацией: старое
значение строки, новое значение, откуда пришло, какая операция, когда. То есть
сообщение — это не строка таблицы, а конверт, внутри которого строка. Как
письмо в конверте: внутри лист (данные), снаружи адрес, штампы, дата
(метаданные). Подробно — в следующем разделе, потому что именно на этом
построена вся разница между `slim` и `full`.

## 4. Что такое `slim` и `full` (и почему их два)

Это **два варианта настройки одного и того же коннектора**. Отличаются они
только тем, **что кладётся в сообщение**. Работают по отдельности: в реальной
эксплуатации используется один — `slim`.

### Профиль `full` — как Debezium делает «из коробки»

Полный конверт. Для изменения одной строки таблицы `catalog.suppliers`
(4 колонки: `id`, `name`, `region_id`, `created_at`) в сообщение едет:

```
конверт:
  before      ← вся строка ДО изменения (4 колонки)
  after       ← вся строка ПОСЛЕ изменения (4 колонки)
  source      ← 14 служебных полей: version, connector, name, ts_ms,
                snapshot, db, sequence, ts_us, ts_ns, schema, table,
                txId, lsn, xmin
  op          ← что за операция: c=вставка, u=обновление, d=удаление
  ts_ms       ← время
  ts_us, ts_ns← то же время в микро- и наносекундах
  transaction ← метаданные транзакции
```

Итого **8 полей верхнего уровня**, внутри которых ~22 поля. Из них по делу —
4 колонки в `after`. Замер: **192 байта на сообщение**.

Обратите внимание на `source`: поля `version`, `connector`, `name`, `db` —
одни и те же в каждом сообщении за всё время работы коннектора. Они описывают
не событие, а сам коннектор, и повторяются миллиард раз.

### Профиль `slim` — то, что используем

Конверт вскрывается и выбрасывается, едет сам лист. Для той же строки:

```
  id, name, region_id, created_at   ← сама строка, как в таблице
  __op        ← операция (c / u / d)
  __table     ← имя таблицы
  __schema    ← имя схемы
  __lsn       ← позиция в WAL: по ней определяется порядок
  __txId      ← номер транзакции
  __ts_ms     ← время
  __deleted   ← "true", если это удаление
```

Итого **строка плюс 7 служебных полей**. Замер: **71 байт на сообщение**.

Так выглядит настоящее сообщение из топика (вывод `make verify` показывает то
же самое таблицей):

```json
{"code":"X07","name":"Test Currency 1","minor_unit":2,
 "__op":"c","__table":"currencies","__schema":"ref",
 "__lsn":83886232,"__txId":769,"__ts_ms":1788793622995,"__deleted":"false"}
```

Первые три поля — это и есть строка таблицы `ref.currencies`. Всё остальное —
служебное. Ключ сообщения отдельно: `{"code":"X07"}`, то есть первичный ключ.

### Зачем нужен второй профиль, если используем первый

`full` нужен ровно для двух вещей:

1. **Чтобы измерить разницу и иметь чем обосновать выбор.** Не «мы считаем, что
   так компактнее», а «замерено: 71 байт против 192, в 2,7 раза, вот как
   мерили». Это аргумент для согласования.
2. **Как запасной вариант.** Единственное, что реально теряется в `slim` — это
   `before`, старое значение строки. Для записи в MS SQL оно не нужно (там
   обновление и удаление идут по первичному ключу). Но если на согласовании
   потребуют старый образ строки — например, для аудита, — переключение
   существует и проверено.

**Что делать вам:** ничего. Работает `slim`, он поднимается командой
`make connector`. Профиль `full` поднимается только внутри замера
(`make benchmark`) и в обычной работе не нужен.

### Топик один — почему тогда контрактов много

Частая и понятная путаница. Топик действительно **один: `cdc.events`**, одна
партиция, туда едут все таблицы. Но **у топика в Kafka не бывает «своей»
схемы**: схема — свойство сообщения, а не топика.

В Avro-сообщении первый байт — маркер, следующие четыре — **номер схемы**, и
только потом данные:

```
[0x00][4 байта: id схемы][бинарные поля]
```

Поэтому подряд идущие сообщения одного топика легально имеют разную структуру.
Вот живой топик со стенда:

| offset | id схемы | чья это схема |
|---:|---:|---|
| 34 | 8 | `catalog.suppliers` |
| 35 | 10 | `catalog.products` |
| 36 | 12 | `sales.customers` |
| 37 | 14 | `sales.orders` |
| 38 | 16 | `sales.order_items` |

Схем у одного топика столько же, сколько таблиц, умноженное на два (на ключ и
на значение): для 8 таблиц — 16, для 500 таблиц будет около тысячи. Отсюда и
поднятый лимит кэша схем, и обязательная `TopicRecordNameStrategy` — иначе
Schema Registry попытается уложить все таблицы в один контракт и откажет на
второй же.

**Поэтому в `contracts/` файл на таблицу, а не файл на топик** — файла на топик
не может быть в принципе.

А общее у всех сообщений топика — семь служебных полей (`__op`, `__table`,
`__schema`, `__lsn`, `__txId`, `__ts_ms`, `__deleted`). Вот это и есть
«контракт топика»: служебные поля consumer знает заранее, а набор колонок
узнаёт из схемы по её номеру. Таблица со всеми полями —
[contracts/README.md](contracts/README.md).

## 6. Что такое Makefile

`Makefile` — это файл со **списком готовых команд под короткими именами**.
`make up` означает «выполни то, что в Makefile записано под именем `up`».

Здесь он используется не как система сборки (компилировать нечего), а как
**справочник операций**: настоящие команды длинные и с деталями, которые легко
забыть или перепутать. Например, за `make verify` стоит запуск скрипта с
переменными окружения, а за `make up-sink` — `docker compose` с указанием
профиля. Помнить это всё не нужно.

Выглядит внутри так:

```makefile
verify: ## проверка порядка по фактическому содержимому топика
	./scripts/verify-order.sh
```

Первая строка — имя цели и, после `##`, описание. Вторая строка (обязательно с
отступом табуляцией) — что выполнить. Всё, никакой магии.

Единственная команда, которую стоит запомнить:

```bash
make help
```

Она печатает список всех целей с описаниями — то есть Makefile сам себе
документация. Полезное следствие: **если операции нет в `make help`, её,
скорее всего, и не нужно делать вручную.**

`make` есть на macOS и Linux из коробки. На Windows — через WSL. Если `make`
почему-то недоступен, ничего не потеряно: откройте `Makefile` и скопируйте
команду из нужной цели руками, это обычные однострочники.

## 7. Что за бенчмарк и что он ответил

Вопрос, на который он отвечает, один: **пролезет ли суточный объём изменений
через один топик с одной партицией?** Потому что если нет — вся архитектура не
годится, и это надо знать до того, как её согласовали.

**Как мерили.** Нельзя просто писать в базу и смотреть, как быстро появляются
сообщения: так измеряется скорость записи в PostgreSQL, а не скорость доставки.
Поэтому: коннектор ставится на паузу, в базу пишется 100 000 изменений (они
копятся в журнале), потом пауза снимается — и замеряется, за сколько коннектор
разгребёт накопленное. Время берётся по метке времени самих сообщений в Kafka.

**Что получилось** (подробно — README, раздел 5):

| | значение |
|---|---|
| скорость | **56 000–87 000 событий в секунду** |
| размер сообщения, `slim` | 71 байт (10 байт после сжатия) |
| размер сообщения, `full` | 192 байта (30 байт после сжатия) |
| за сутки | **4,9–7,6 млрд событий**, 47–73 ГБ на диске |

**Ответ:** пролезет с большим запасом. Поток в 100 млн изменений в сутки —
это 2% от измеренного потолка. Так что порядок сообщений не приходится
разменивать на производительность.

Побочно бенчмарк подобрал одну настройку: **`linger.ms = 50`**. Это задержка
перед отправкой, которая позволяет собрать сообщения в пачку и сжать их вместе.
Без неё — 18,9 байта на сообщение на диске, с ней — 10,4. То есть **одна строка
конфига даёт экономию диска почти в 2 раза**.

## 8. Первые 10 минут: что запустить

```bash
make up
```

Поднимает всё: PostgreSQL с двумя репликами, Kafka, справочник схем, Kafka
Connect. Первый раз дольше — качаются образы. В конце покажет список сервисов;
все должны быть `healthy`, а `pg-init` и `kafka-init` — `Exited (0)` (это
одноразовые задачи, они отработали и вышли).

```bash
make connector
```

Включает собственно CDC. Отдельной командой намеренно: важно, что слот в базе
создаётся раньше коннектора.

```bash
make load
```

Делает изменения в базе — чтобы было что смотреть.

```bash
make verify
```

## 10. Как добавить свои таблицы

Самый частый вопрос, поэтому конкретно и по шагам. Процедура **проверена на
стенде**, не выдумана: я добавил схему `billing` с таблицей `invoices`, прогнал
её по этим шагам и увидел событие в топике.

Есть два случая, и они сильно разной сложности.

### Случай А: таблица в схеме, которая уже в CDC

Например, добавляете `sales.refunds` — схема `sales` уже включена.

```bash
# 1. Создайте таблицу своим DDL. ОБЯЗАТЕЛЬНО с PRIMARY KEY (почему — ниже).
#    На стенде это sql/02-schemas.sql, в контуре — ваша миграция.

# 2. Добавьте её в публикацию. Либо руками:
#      ALTER PUBLICATION dbz_cdc_pub ADD TABLE sales.refunds;
#    либо просто:
make up          # pg-init сам добавит все таблицы схем из CDC_SCHEMAS

# 3. Ничего больше. Коннектор перезапускать НЕ надо.
#    Он увидит таблицу при первом же изменении в ней.

# 4. Проверьте и зафиксируйте контракт:
make verify      # таблица должна появиться в статистике по таблицам
make contracts   # выгрузит новую Avro-схему
git add contracts/generated && git commit
```

### Случай Б: новая схема

Например, добавляете схему `billing`. **Одна правка в одном файле:**

```bash
# 1. Ваш DDL создал схему billing и таблицы в ней (с PRIMARY KEY).

# 2. Одна строка в .env:
#      CDC_SCHEMAS=ref,catalog,sales,billing
#    Это ЕДИНСТВЕННОЕ место, где перечислены схемы CDC. Отсюда значение
#    попадает и в публикацию, и в гранты роли debezium, и в
#    schema.include.list коннектора.

# 3. Применить:
make up          # pg-init добавит таблицы новой схемы в публикацию
                 # и выдаст роли debezium USAGE/SELECT на неё
make connector   # коннектор перечитает schema.include.list

# 4. Проверить и зафиксировать:
make verify
make contracts
```

Так это выглядело на стенде при проверке:

```
psql:/sql/04-publication.sql: NOTICE:  в публикацию dbz_cdc_pub добавлена billing.invoices
[OK]   конфиг коннектора pg-cdc обновлён
schema.include.list = ref,catalog,sales,billing

  offset  part lsn        txId  schema.table        op  pk
  33      0    84711304   845   billing.invoices    c   id=1
```

И в справочнике схем сразу появились `cdc.events-dbz.billing.invoices.Key` и
`...Value`.

### Три требования к таблице

1. **PRIMARY KEY обязателен.** Без него `REPLICA IDENTITY DEFAULT` нечего
   отдавать, и события UPDATE/DELETE приедут без ключа — приёмнику будет нечем
   найти строку в MS SQL. Если PK нет и добавить нельзя, для этой таблицы
   придётся ставить `REPLICA IDENTITY FULL` точечно (переменная
   `REPLICA_IDENTITY_FULL`), понимая цену: полный старый образ строки в WAL на
   каждое изменение.
2. **Тяжёлые колонки лучше исключить.** Blob'ы и большие тексты, которые
   приёмнику не нужны, добавьте в `column.exclude.list` в
   `connector/slim.jsonc` — формат `схема.таблица.колонка` через запятую.
3. **Данных «до» не будет.** Изменения попадают в поток только с момента, когда
   таблица оказалась в публикации. То, что лежало в ней раньше, придётся
   залить в (Б) отдельно — так же, как заливались остальные данные на момент T.

### Чего делать НЕ надо

- **не создавать топик под новую таблицу** — все таблицы едут в один
  `cdc.events`, это и есть главный принцип проекта;
- **не добавлять таблицу в `table.include.list`** — такого списка здесь нет
  специально: на 500 таблиц он неуправляем, состав ведётся публикацией;
- **не перезапускать Connect** — достаточно `make connector`, а в случае А не
  нужно и этого.

### Как убрать таблицу из CDC

```sql
ALTER PUBLICATION dbz_cdc_pub DROP TABLE sales.refunds;
```

Либо, если таблица должна остаться в публикации, но не уезжать в Kafka —
добавьте её в `table.exclude.list` в `connector/slim.jsonc` и сделайте
`make connector`. Именно так в проекте исключена демонстрационная
`sales.order_items_archive`.

Её старая Avro-схема останется в справочнике схем — так и надо. Схемы не
удаляются автоматически, ничего не стоят и никому не мешают.

**Удалять их вручную нельзя**, пока в топике есть сообщения с этой схемой:
в сообщении записан её номер, и после удаления consumer не сможет прочитать
такое сообщение вообще (`Schema N not found`). Восстановить не получится —
повторная регистрация выдаёт новый номер. Я на это наступил на стенде: лечится
только пересозданием топика. Подробно — README, раздел 8.

## 11. Что вам реально нужно отсюда

Три разных пакета для трёх разных людей.

### Если вы отдаёте задачу devops

Раздел 2 в [README.md](README.md) — готовый чеклист, копируется как есть:
настройки мастера и реплик, какие слоты создать (с точным SQL), какую
публикацию создать и как её вести, какие права выдать пользователю Debezium и
каких прав у него быть не должно, какие топики создать заранее. Плюс раздел 2.9
— в какой момент создавать слот относительно синхронизации баз. Это самое
важное место всей процедуры.

### Если вы отдаёте задачу разработчику части 2

Раздел 4 в [README.md](README.md) плюс папка [contracts/](contracts/README.md).
Там семь вещей, которые он обязан сделать правильно, иначе данные разъедутся
незаметно: читатель ровно один (параллелить нельзя), разбор по номеру схемы, а
не по имени таблицы, хранение последнего LSN **в той же транзакции**, что и
данные, и коммит позиции в Kafka **после** коммита в MS SQL.

### Если вы идёте на согласование

Два раздела README:

- **раздел 9** — расхождения версий. Одно блокирующее (avro-converter 6.x с
  Kafka 3.7 не работает вообще), одно желательное (Debezium 2.6.2 вместо
  2.6.1 — там починена потеря событий при перезапуске), один открытый вопрос
  (Schema Registry «v1.17.1» — такой версии не существует, надо выяснить, что
  это);
- **раздел 5** — цифры производительности и вывод о применимости.

Плюс одно, о чём надо сказать явно: **ограничение «Debezium не создаёт слоты»
техническими средствами не обеспечивается**. Проверено на стенде: PostgreSQL не
умеет запретить создание слота пользователю, который имеет право читать поток
(а без этого права Debezium не работает), и Debezium сам создаёт отсутствующий
слот — причём без флага `failover`, то есть незаметно ломая переключение
мастера. Вместо запрета нужен **мониторинг**: алерт на логические слоты с
`failover = false`. Это единственная надёжная защита, и её надо завести в
эксплуатации.

## 13. Одна вещь, которую стоит запомнить

Если из всего проекта запоминать что-то одно, то вот это:

> **Порядок сообщений держится на трёх настройках producer'а, которые работают
> только вместе:** `enable.idempotence=true`, `acks=all`,
> `max.in.flight.requests.per.connection <= 5`. Если убрать первую, оставив
> третью, порядок сломается — **и сломается тихо**, без ошибок и алертов, до
> того момента, когда читатель части 2 упрётся в нарушение связи между
> таблицами. К тому времени в MS SQL уже будет мусор.

Поэтому в конфиге эти строки стоят рядом с комментарием, а `make verify-infra`
проверяет их **по фактическому состоянию коннектора**, а не по файлу в
репозитории — потому что расходятся именно они. Механика происходящего
объяснена в [CLAUDE.md](CLAUDE.md), раздел «что НЕ делать».
