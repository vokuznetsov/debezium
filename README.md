## 1. Что делает проект

Держит синхронными две базы: **(А)** PostgreSQL (источник, ~500 таблиц в
разных схемах, межсхемные внешние ключи) и **(Б)** MS SQL (приёмник). Базы
синхронизированы на момент T, дальше (А) работает в live.

Задача из двух частей. **Реализована первая**: (А) → Kafka.

### Два инварианта, которые не обсуждаются

**Инвариант №1 — порядок.** Изменения ВСЕХ таблиц ВСЕХ схем идут в один топик
с одной партицией, строго в порядке WAL. Consumer части 2 применяет их
последовательно и не разбирает порядок foreign key на своей стороне.

**Инвариант №2 — объём.** Полная синхронизация должна укладываться в сутки,
каждый лишний байт умножается на объём потока. Размер сообщения — второй по
важности критерий после порядка.

### Два следствия failover-слота, которые надо знать сразу

1. **С синхронизированного слота на реплике читать нельзя до промоушена** —
   PostgreSQL это прямо запрещает:

   ```
   ERROR:  cannot use replication slot "dbz_cdc_slot" for logical decoding
   DETAIL: This replication slot is being synchronized from the primary server.
   ```

   Иногда та же попытка отбивается другой формулировкой — если слот прямо
   сейчас держит slotsync-воркер реплики:

   ```
   ERROR:  replication slot "dbz_cdc_slot" is active for PID 32
   ```

   Обе означают одно: Debezium ходит только на мастер, и **разгрузить CDC на
   реплику невозможно**.

2. **`synchronized_standby_slots` ставит CDC в зависимость от доступности
   реплик**: мастер придерживает walsender'ы логического слота, пока
   перечисленные физические слоты не подтвердят приём WAL. Отстала реплика —
   притормозил поток CDC. Это осознанный размен: целостность при failover в
   обмен на независимость от здоровья standby.

## 2. Что должен сделать devops ДО разворачивания

Этот раздел можно отдать как есть.

### 2.1 Параметры мастера

```ini
wal_level = logical                    # обязательно для pgoutput
max_replication_slots = 12             # 2 физических + 1 логический CDC + резерв
max_wal_senders = 12                   # столько же
hot_standby = on
wal_keep_size = 1GB                    # подстраховка на время пересоздания слота
synchronized_standby_slots = 'replica_1_slot,replica_2_slot'
log_replication_commands = on          # чтобы было видно, кто создаёт слоты
# max_slot_wal_keep_size НЕ ограничивать без мониторинга лага слота:
# при превышении Postgres ИНВАЛИДИРУЕТ слот, а это полная пересинхронизация CDC
```

`synchronized_standby_slots` обязан перечислять ровно те слоты, которые
используют реплики. Расхождение не проявляется до момента переключения.

### 2.2 Параметры реплик

```ini
sync_replication_slots = on            # включает slotsync-воркер
hot_standby_feedback = on              # обязателен для синхронизации слотов
hot_standby = on
wal_level = logical
primary_slot_name = 'replica_1_slot'   # у каждой реплики СВОЙ
# primary_conninfo ОБЯЗАН содержать dbname — без него slotsync-воркер
# молча не работает:
# primary_conninfo = 'host=pg-master port=5432 user=replicator dbname=cdc ...'
#
# synchronized_standby_slots НА РЕПЛИКАХ НЕ ЗАДАВАТЬ. После промоушена узел
# начнёт придерживать walsender'ы до подтверждения от слотов, которых на нём
# нет, и поток CDC встанет насовсем без внятной ошибки.
```

### 2.3 Физические слоты под реплики

```sql
SELECT pg_create_physical_replication_slot('replica_1_slot', true, false);
SELECT pg_create_physical_replication_slot('replica_2_slot', true, false);
--                                                          ^^^^ immediately_reserve:
-- слот резервирует WAL сразу, а не при первом подключении реплики
```

Создать **до** снятия базовой копии: `pg_basebackup` вызывается с
`-S <slot>` и без `-C`, то есть слот обязан уже существовать.

```bash
pg_basebackup -d "host=pg-master port=5432 user=replicator dbname=cdc" \
              -D "$PGDATA" -R -X stream -S replica_1_slot -c fast -P -v
```

### 2.4 Логический слот CDC — точный SQL

```sql
SELECT pg_create_logical_replication_slot('dbz_cdc_slot', 'pgoutput',
                                          false,   -- temporary
                                          false,   -- two_phase
                                          true);   -- failover  <-- ОБЯЗАТЕЛЬНО
```

**Почему флаг `failover` обязателен.** Логические слоты живут только на
мастере. Без него переключение на реплику означает потерю слота и **полную
пересинхронизацию CDC**: (Б) придётся заливать заново. В PostgreSQL 17 слот с
`failover => true` синхронизируется на реплики встроенным slotsync-воркером и
после промоушена уже есть на новом мастере, с подтверждённым LSN.

**Debezium этот флаг сам не выставляет** (в 2.6 не реализовано, DBZ-8412), а
выставить его постфактум у существующего слота нельзя — только пересоздать, а
пересоздание = потеря позиции. Поэтому слот создаётся сразу правильным.

Проверка:

```sql
SELECT slot_name, slot_type, plugin, failover, synced, active,
       restart_lsn, confirmed_flush_lsn, invalidation_reason
FROM pg_replication_slots;
```

На мастере ожидается `failover = t`, на репликах тот же слот с `synced = t`.

### 2.5 Публикация и её состав

```sql
CREATE PUBLICATION dbz_cdc_pub WITH (publish = 'insert, update, delete');
--                                             ^ без truncate: в профиле slim
--                                               эти события всё равно теряются,
--                                               а TRUNCATE на приёмнике — отдельная
--                                               согласованная процедура
ALTER PUBLICATION dbz_cdc_pub ADD TABLE ref.currencies;
ALTER PUBLICATION dbz_cdc_pub ADD TABLE ref.regions;
-- ... и так по всем таблицам, входящим в CDC
```

Состав CDC живёт **в SQL**, а не в `table.include.list` коннектора: список на
500 строк в JSON неуправляем. Коннектор фильтрует грубо
(`schema.include.list`) и точечно исключает (`table.exclude.list`).

**Процедура добавления таблицы** (пошагово и с проверенным примером —
[START-HERE.md, раздел 10](START-HERE.md#10-как-добавить-свои-таблицы)):

0. Если таблица в **новой схеме** — сначала добавить схему в `CDC_SCHEMAS` в
   `.env`. Это единственное место, где перечислены схемы CDC: отсюда значение
   попадает и в состав публикации (`sql/04-publication.sql`), и в гранты роли
   `debezium` (`sql/02-schemas.sql`), и в `schema.include.list` коннектора.
   После правки — `make up && make connector`.
1. `ALTER PUBLICATION dbz_cdc_pub ADD TABLE <схема>.<таблица>;`
   (или `make up` — `pg-init` добавит все таблицы схем из `CDC_SCHEMAS`)
2. Убедиться, что `REPLICA IDENTITY` у неё `DEFAULT` (то есть есть PK).
3. **Рестарт коннектора не нужен.** Debezium увидит таблицу, как только по ней
   придёт первое событие из `pgoutput`.
4. Но данные, которые были в таблице **до** добавления в публикацию, в топик
   не попадут. Для них нужен ad-hoc снапшот или отдельная заливка в (Б).
5. Новая Avro-схема появится в Schema Registry автоматически (на стенде;
   в контуре при `auto.register.schemas=false` её надо зарегистрировать
   заранее). После этого — `make contracts` и коммит.

Альтернатива, о которой стоит знать: `CREATE PUBLICATION ... FOR TABLES IN
SCHEMA ref, catalog, sales` — новые таблицы попадают в публикацию сами. Не
выбрано сознательно: теряется контроль над составом (любая новая таблица сразу
уезжает в CDC) и нельзя опубликовать подмножество колонок.

### 2.6 REPLICA IDENTITY

```sql
ALTER TABLE <схема>.<таблица> REPLICA IDENTITY DEFAULT;   -- только PK
```

`DEFAULT` на всех таблицах. `FULL` пишет в WAL полный **старый** образ строки
на каждый UPDATE/DELETE — на 500 таблицах это кратный рост WAL и объёма
сообщений, то есть прямое нарушение инварианта №2. Для применения в MS SQL
достаточно `after`-образа и PK.

`FULL` — точечно, по явному обоснованию. В стенде для этого есть переменная
`REPLICA_IDENTITY_FULL` (список таблиц через запятую), которую читает
`sql/04-publication.sql`.

### 2.7 Права пользователя Debezium

**Что нужно выдать:**

```sql
CREATE ROLE debezium WITH LOGIN REPLICATION
       NOSUPERUSER NOCREATEDB NOCREATEROLE PASSWORD '...';
GRANT USAGE ON SCHEMA ref, catalog, sales TO debezium;
GRANT SELECT ON ALL TABLES IN SCHEMA ref, catalog, sales TO debezium;
ALTER DEFAULT PRIVILEGES IN SCHEMA ref, catalog, sales
      GRANT SELECT ON TABLES TO debezium;
```

- `REPLICATION` — открыть replication-соединение и читать поток `pgoutput`;
- `SELECT`/`USAGE` — прочитать структуру таблиц из каталога (при
  `snapshot.mode=no_data` данные не вычитываются, но SELECT нужен для
  валидации и для точечного ad-hoc снапшота).

**Чего быть не должно:**

```sql
REVOKE CREATE ON DATABASE cdc FROM PUBLIC, debezium;   -- не сможет создать публикацию
REVOKE EXECUTE ON FUNCTION
    pg_catalog.pg_create_logical_replication_slot(name, name, boolean, boolean, boolean)
    FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION
    pg_catalog.pg_create_physical_replication_slot(name, boolean, boolean) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION pg_catalog.pg_drop_replication_slot(name) FROM PUBLIC;
```

и никаких `SUPERUSER`, `CREATEDB`, `CREATEROLE`.

> **Оговорка, проверенная на стенде — прочитать обязательно.**
>
> Полностью запретить создание слота роли с атрибутом `REPLICATION`
> **невозможно**. Команда `CREATE_REPLICATION_SLOT` идёт по репликационному
> протоколу и проверяет только сам атрибут, а без него Debezium не прочитает
> поток вообще. Отдельного права «читать готовый слот, но не создавать» в
> PostgreSQL нет. Проверка на стенде:
>
> ```
> $ psql "host=pg-master user=debezium dbname=cdc replication=database" \
>        -c "CREATE_REPLICATION_SLOT probe LOGICAL pgoutput"
>  slot_name | consistent_point | snapshot_name | output_plugin
>  probe     | 0/5058248        | ...           | pgoutput      <-- получилось
> ```
>
> Более того, **Debezium 2.6 сам создаёт отсутствующий слот и штатно
> стартует**: `publication.autocreate.mode=disabled` управляет только
> публикациями, опции «не создавать слот» у коннектора нет. Проверено
> `verify-infra.sh`: коннектор с `slot.name=probe_noslot_*` вышел в RUNNING,
> создав слот **с `failover = f`**.
>
> Практический вывод: **запрет на создание слотов держится не на правах, а на
> контроле состояния.** Обязательно иметь алерт на
> `pg_replication_slots WHERE slot_type='logical' AND NOT failover` и на
> появление логических слотов вне утверждённого списка. Именно это проверяет
> `make verify-infra`.
>
> Права на публикации при этом закрыты по-настоящему:
> `ERROR: permission denied for database cdc`.

### 2.8 Топики Kafka

Создать **заранее**, все до единого. Auto-create должен быть **выключен**
(`auto.create.topics.enable=false` на брокере, `topic.creation.enable=false` на
воркере Connect), поэтому отсутствующий топик роняет сервис, а не появляется
сам с дефолтной политикой очистки.

| топик | партиций | `cleanup.policy` | зачем |
|---|---:|---|---|
| `cdc.events` | **1** | `delete` | основной поток |
| `dbz.transaction` | 1 | `delete` | метаданные транзакций |
| `__debezium-heartbeat.dbz` | 1 | `delete` | heartbeat |
| `connect-configs` | 1 | `compact` | внутренний Connect |
| `connect-offsets` | 25 | `compact` | внутренний Connect |
| `connect-status` | 5 | `compact` | внутренний Connect |
| `_schemas` | 1 | `compact` | Schema Registry |

`__consumer_offsets` — исключение: его создаёт координатор групп брокера,
`auto.create.topics.enable` на него не влияет.

Числа партиций служебных топиков Connect обязаны совпадать с
`CONNECT_OFFSET_STORAGE_PARTITIONS=25` и `CONNECT_STATUS_STORAGE_PARTITIONS=5`,
иначе воркер не стартует.

> **На `cdc.events` compaction запрещён при любых условиях.**
> `cleanup.policy=compact` оставляет только последнюю версию записи по ключу и
> выбрасывает промежуточные. Для потока CDC это уничтожение самой идеи
> последовательного применения: приёмник получит не историю изменений, а
> случайный срез, и дедупликация по LSN этого не восстановит. Единственно
> допустимое значение — `delete`. Retention на `cdc.events` — это окно, за
> которое consumer обязан успеть прочитать поток (на стенде 7 суток).

### 2.9 Когда создавать слот относительно момента синхронизации

Это самое важное место всей процедуры.

```
   момент T                                                    время
   ────────┬───────────────┬─────────────────┬──────────────────▶
           │               │                 │
   (А) и (Б)          СОЗДАТЬ СЛОТ      поднять коннектор
   синхронизированы    dbz_cdc_slot      snapshot.mode=no_data
   внешним способом
           │               │                 │
           │               └──── WAL с этой точки УДЕРЖИВАЕТСЯ ──▶
           │                     и доедет в топик, даже если
           │                     коннектор поднят намного позже
           │
           └── изменения ДО слота в топик НЕ попадут:
               они уже применены в (Б)
```

Порядок:

1. Синхронизировать (А) и (Б) любым внешним способом (bulk-заливка, бэкап).
2. **Сразу после этого создать логический слот** — с этого момента WAL
   удерживается и ни одно изменение не потеряется.
3. Коннектор можно поднимать позже, в удобное окно. Изменения, сделанные между
   созданием слота и старом коннектора, доедут.

Граница «что попадёт в топик» проходит **по моменту создания слота, а не по
моменту старта коннектора**. Именно это доказывает `make scenario`
(см. раздел 3).

Обратный порядок (сначала слот, потом заливка) даст в топике события `op=c` по
уже синхронизированным строкам, и consumer части 2 применит в (Б) то, что там
уже есть.

## 3. Запуск и проверка

Запускается всё **с хоста**, но вся работа идёт в контейнерах: на хосте нужны
только `docker`, `make`, `bash`, `awk`. `jq` — опционально: если его нет,
скрипты берут его из контейнера. `psql`, `kafka-topics`, `kcat`,
`kafka-avro-console-consumer` и `curl` всегда берутся из контейнеров стенда,
поэтому проверки проверяют именно те версии клиентов, что стоят в стенде.

### 3.1 Первый запуск

```bash
make up          # собрать образ Connect, поднять PG-кластер, Kafka, SR, Connect
make connector   # поставить коннектор, профиль slim
make load        # смешанная нагрузка
make verify      # проверка порядка
```

`make up` заканчивается так:

```

Коннектор НЕ создаётся автоматически: make connector

`sink` и поднимается отдельно — `make up-sink`. Причина в образе: он
существует только под `linux/amd64`, на arm64-хосте идёт через эмуляцию
(~2 ГБ RAM, минута на старт), а в части 1 не используется вообще.

```

### 3.3 Проверка ограничений эксплуатации — `make verify-infra`

Восемь шагов: слот и его `failover`; кто создавал слот (по логу
`log_replication_commands`); `synced` на репликах и запрет чтения
синхронизированного слота; права роли `debezium` (включая негативные
проверки); auto-create топиков и отсутствие лишних; **жёсткая проверка связки
гарантий порядка по фактическому конфигу коннектора через REST**; проверка,
что `producer.override.*` реально применился; отсутствие посторонних
логических слотов.

Самое ценное — шаг 6. Он читает из лога воркера фактический `ProducerConfig`
задачи и сверяет его с `.env`:

```
--- фактический ProducerConfig задачи (из лога воркера) ---
    ищем блок ProducerConfig с client.id = connector-producer-pg-cdc-0
      acks = -1
      batch.size = 262144
      compression.type = zstd
      enable.idempotence = true
      linger.ms = 50
      max.in.flight.requests.per.connection = 5
  [OK]   фактически enable.idempotence=true
  [OK]   фактически acks=-1 (-1 = all)
  [OK]   фактически max.in.flight=5 (= MAX_IN_FLIGHT из .env)
    совпадение фактических значений с .env и есть доказательство, что override работает
```

Без `connector.client.config.override.policy=All` на воркере Connect **молча
проигнорирует** все `producer.override.*` и возьмёт настройки воркера. Конфиг
коннектора будет выглядеть правильным, а гарантий не будет — ни ошибки, ни
предупреждения. Проверять надо именно фактический `ProducerConfig`.

Два **предупреждения** в выводе `verify-infra` — не дефекты, а
задокументированные свойства PostgreSQL и Debezium (раздел 2.7): роль с
`REPLICATION` может создать слот по протоколу, и Debezium создаёт
отсутствующий слот сам, причём без `failover`.

### 3.6 Работа с томами: `down`, `clean`, `reset-cdc`

```bash
make down        # остановить, ДАННЫЕ СОХРАНИТЬ
make up          # продолжить с прежнего LSN
```

Проверено на стенде. До `make down`:

```
cdc.events: 2040280 сообщений
     slot_name     | failover | active | confirmed_flush_lsn
 dbz_cdc_slot      | t        | t      | 0/18494FE0
 dbz_cdc_slot_full | t        | t      | 0/18494FE0

```

После `make up` — то же самое, без единого расхождения:

```
cdc.events: 2040280 сообщений
строк в sales.order_items: 2040088
     slot_name     | failover | active | confirmed_flush_lsn
 dbz_cdc_slot      | t        | t      | 0/18494FE0
 dbz_cdc_slot_full | t        | t      | 0/18494FE0
коннекторы: ["pg-cdc","pg-cdc-full"]
состояние pg-cdc: RUNNING / задача RUNNING
```

Коннектор продолжил с прежней позиции сам: и подтверждённый LSN в слоте, и
offset'ы в `connect-offsets` лежат в томах. Пересоздавать коннектор после
`make up` не нужно — его конфиг хранится в `connect-configs`.

```bash
make clean       # ПОЛНЫЙ сброс: down -v, все тома (с подтверждением)
```

**Почему `clean` сносит всё разом.** Состояние PostgreSQL и Kafka описывает
**одну точку**: подтверждённый LSN в слоте и offset'ы в `connect-offsets` —
две половины одного факта «докуда доехало». Сбросить их по отдельности нельзя:

- **снесли Kafka, оставили PostgreSQL** → offset'ы пропали, слот хранит старый
  подтверждённый LSN. Коннектор поедет от позиции слота и при
  `snapshot.mode=no_data` даст неконсистентное состояние приёмника: часть
  изменений приедет повторно (это переживаемо, consumer дедуплицирует по LSN),
  но часть топика уже удалена вместе с томом Kafka, а слот её больше не
  отдаст — эти изменения потеряны безвозвратно;
- **снесли PostgreSQL, оставили Kafka** → слот создан заново, на текущем LSN, а
  `connect-offsets` ссылаются на LSN, которого в новом кластере уже не
  существует. Коннектор падает при попытке начать чтение с несуществующей
  позиции.

Поэтому либо `clean` целиком, либо согласованный сброс только CDC:

```bash
make reset-cdc   # удалить коннектор, пересоздать слот и cdc.events/connect-offsets
                 # данные в PostgreSQL остаются
```

`reset-cdc` сбрасывает ровно то, что относится к CDC, и сбрасывает это
согласованно. **После него состояние (Б) становится несогласованным с (А)**:
новый слот начинает с текущего LSN, изменения между старым подтверждённым LSN
и новым потеряны. Значит после `reset-cdc` базы нужно синхронизировать заново
— это новый момент T. Скрипт предупреждает и требует подтверждения.

## 4. Как consumer должен читать этот топик

Раздел для того, кто будет писать часть 2. Вопрос, на который он отвечает: «в
одном топике лежат события 500 таблиц из разных схем, что с этим делать».

### 4.1 Читатель ровно один

Топик один, партиция одна — значит **параллелить нельзя**. Consumer group с
двумя участниками бессмысленна: партиция назначается одному участнику, второй
не получит ничего. Любая попытка распараллелить применение разрушает инвариант
№1, ради которого весь этот топик и устроен так, как устроен.

### 4.2 Consumer не должен знать 500 схем заранее

В Avro-сообщении первые байты — магический байт и **идентификатор схемы**.
`KafkaAvroDeserializer` сам забирает схему из Schema Registry по этому id и
отдаёт `GenericRecord`. Никаких сгенерированных классов, никакого
предварительного знания о таблицах.

Это проверяется прямо на стенде: `kafka-avro-console-consumer` читает поток из
десятков разных схем, имея в конфиге `value.subject.name.strategy =
TopicNameStrategy` (то есть «неправильную» стратегию) — и всё равно
десериализует корректно, потому что **разбор идёт по id схемы из сообщения, а
не по имени subject'а**. Стратегия именования важна только при регистрации.

### 4.3 Как определить исходную таблицу

Три независимых способа, все доступны без внешнего знания:

1. поля `__schema` и `__table` в профиле `slim`
   (в профиле `full` — `source.schema` / `source.table`);
2. **полное имя Avro-рекорда**: `dbz.catalog.products.Value` — оно однозначно
   определяет таблицу и меняется вместе с её структурой;
3. subject в Schema Registry: `cdc.events-dbz.catalog.products.Value`.

### 4.4 Как строить SQL: кэш по id схемы, а не по имени таблицы

Ключом кэша подготовленных выражений должен быть **id схемы из сообщения**, а
не имя таблицы:

```
prepared = cache.get(schemaId)            // НЕ cache.get(tableName)
if (prepared == null) {
    prepared = buildStatement(record.getSchema())   // MERGE/INSERT/UPDATE/DELETE
    cache.put(schemaId, prepared)
}
```

Почему так: при изменении структуры таблицы Debezium регистрирует **новую
версию схемы с новым id**, и ключ кэша меняется автоматически. При
кэшировании по имени таблицы пришлось бы отдельно замечать изменение и
инвалидировать кэш — а не заметить его легко, потому что DDL-событий
PostgreSQL-коннектор не отдаёт (см. 4.8).

### 4.5 Тип операции

| `__op` | что делать в (Б) |
|---|---|
| `c` | вставка (create) |
| `r` | вставка (read — событие снапшота; при `snapshot.mode=no_data` не приходит) |
| `u` | обновление по PK |
| `d` | удаление по PK |

При `delete.handling.mode=rewrite` удаление приезжает **строкой с
`__deleted="true"`**, а не пустым значением (tombstone). Tombstone'ов в потоке
нет вообще: `tombstones.on.delete=false` и `drop.tombstones=true` — compaction
на топике выключен и запрещён, поэтому tombstone'ы никому не нужны, а каждый
DELETE давал бы второе сообщение.

Практически: обработчик может смотреть только на `__deleted`, а `__op`
использовать для различения вставки и обновления. Или применять всё через
`MERGE` по PK — тогда `c` и `u` обрабатываются одинаково, и повторная доставка
события становится безвредной сама по себе.

### 4.6 Идемпотентность: last_lsn в той же транзакции

```sql
-- служебная таблица в (Б)
CREATE TABLE cdc_state (
    stream_name  varchar(64)  NOT NULL PRIMARY KEY,
    last_lsn     bigint       NOT NULL,
    updated_at   datetime2    NOT NULL
);
```

Правило: **хранить последний применённый `__lsn` и писать его в ТОЙ ЖЕ
транзакции MS SQL, что и данные.** При рестарте пропускать записи с `__lsn`
меньше или равным сохранённому.

```
BEGIN TRANSACTION
    для каждой записи батча в порядке чтения:
        если record.__lsn <= last_lsn: пропустить    -- уже применено
        применить (MERGE / DELETE) по PK
    UPDATE cdc_state SET last_lsn = <__lsn последней записи>, updated_at = SYSUTCDATETIME()
COMMIT
```

Если `last_lsn` писать отдельной транзакцией, появляется окно, в котором
данные применены, а позиция не сохранена (или наоборот) — и после падения
приёмник либо потеряет изменения, либо применит их дважды.

`__lsn` монотонен и уникален в пределах потока — это проверяет
`verify-order.sh` на каждом прогоне. Поэтому сравнение «меньше или равно»
корректно и не требует хранения множества применённых id.

### 4.7 Порядок коммита offset'а

```
1. COMMIT транзакции в MS SQL   (данные + last_lsn)
2. commitSync() offset'а в Kafka   ВРУЧНУЮ
```

**Только в этом порядке. Автокоммит запрещён** (`enable.auto.commit=false`).

Что даёт: если процесс упадёт между шагами 1 и 2, после рестарта Kafka отдаст
батч заново, а дедупликация по `last_lsn` его отфильтрует. То есть
**at-least-once на транспорте + дедупликация по LSN = эффект exactly-once на
приёмнике**, без распределённых транзакций.

Обратный порядок (сначала offset, потом БД) даёт потерю данных при падении в
том же окне — и восстановить их будет нечем: Kafka считает батч обработанным.

### 4.8 Батчинг

- применять пачку записей **в одной транзакции** MS SQL — иначе накладные
  расходы на транзакцию съедят пропускную способность;
- **порядок внутри пачки сохранять** — он и есть порядок WAL;
- коммит offset'а — после коммита транзакции;
- размер пачки подбирать по времени удержания блокировок в (Б), а не по
  максимуму: длинная транзакция в приёмнике блокирует его читателей.

### 4.9 Почему не нужно разбираться с foreign key

Порядок в топике совпадает с порядком в WAL источника, а в источнике
ограничения целостности уже проверены на момент коммита. Значит родительская
строка всегда приходит **раньше** дочерней, и применение строго по порядку
никогда не упирается в constraint.

Это прямое следствие инварианта №1 и главная причина, по которой топик один и
партиция одна. Обратное тоже верно: **любая попытка распараллелить чтение
вернёт проблему разбора FK на сторону consumer'а** — и там её придётся решать
топологической сортировкой по зависимостям, которых consumer не знает.

Видно это на стенде: `make verify` печатает транзакции, где внутри одного
`txId` строки идут валюта → регион → поставщик → товар → покупатель → заказ →
позиция заказа. Цепочка FK глубиной 5 — при перемешанном порядке применение
упрётся в constraint гарантированно.

### 4.10 Изменения структуры таблиц

**Debezium для PostgreSQL не отдаёт DDL-события.** Изменение структуры
проявляется только как **новая версия Avro-схемы** (новый id схемы в
сообщении).

Consumer обязан это замечать и как минимум сигнализировать:

- новый id схемы для уже известного имени рекорда → структура изменилась;
- сравнить набор полей с тем, что есть в (Б);
- добавленная nullable-колонка — обычно безопасно применять автоматически;
- удалённая или переименованная колонка, изменение типа — **останавливаться и
  звать человека**, а не угадывать.

Инструмент для этого — `make contracts`: выгружает все subject'ы из Schema
Registry в `contracts/generated/` и коммитится. Тогда изменение структуры
таблицы в (А) видно в `git diff`, а не обнаруживается по падению consumer'а.

В контуре к этому стоит добавить `auto.register.schemas=false` с
предварительной регистрацией контрактов: тогда неожидаемое изменение структуры
уронит коннектор (громкий отказ), а не уедет в приёмник (тихий).

## 5. Объём и производительность

Все числа ниже — из фактических прогонов `make benchmark` на этом стенде.
Воспроизводится командой:

```bash
BENCH_ROWS=5000 BENCH_TXS=20 BENCH_REPEATS=2 BENCH_LINGER="0 50 200" make benchmark
```

### 5.1 Методика (иначе цифры ничего не значат)

Мерить «пишем в БД и смотрим, как быстро появляются сообщения» нельзя: так
измеряется скорость записи в PostgreSQL, а не пропускная способность
конвейера. Поэтому замер построен на **разборе накопленного отставания**:

1. коннектор ставится на паузу — слот продолжает удерживать WAL;
2. в БД пишется 100 000 изменений (20 транзакций × 5000 строк), они копятся;
3. коннектор снимается с паузы и разбирает отставание на максимальной скорости;
4. время считается **по таймстемпам сообщений в Kafka** (первое и последнее из
   партии), а не по wall-clock скрипта.

Объём считается тремя независимыми числами:

- **wire** — сумма размеров сериализованных сообщений (`kcat -f '%S %K'`), то
  есть то, что видит consumer;
- **на диске** — прирост размера партиции на брокере (`kafka-log-dirs`), то
  есть то, что реально занято **после** компрессии zstd, с накладными
  расходами батчей;
- их отношение — фактический коэффициент сжатия на этом потоке.

Профили сравниваются на **одних и тех же** изменениях: слот профиля `full`
создаётся до нагрузки, поэтому оба коннектора видят одинаковый поток.

### 5.2 Размер сообщения: `slim` против `full`

| профиль | Б/сообщение (wire) | Б/сообщение на диске | сжатие | схема (`catalog.products`) |
|---|---:|---:|---:|---:|
| `slim` | **71,2** | **10,4** | 6,8x | 16 полей, 2115 Б |
| `full` | **192,1** | **30,5** | 6,3x | 37 полей, 5298 Б |
| разница | **в 2,7 раза** | **в 2,9 раза** | — | в 2,5 раза |

То есть плоский формат вместо полного конверта Debezium даёт **экономию в
2,7 раза по трафику и в 2,9 раза по диску** на одинаковой нагрузке. Причина
видна прямо в схемах (`contracts/examples/`): в `full` в каждом сообщении едут
`before` (полная копия строки), блок `source` из 12 полей и `transaction`, а
`version`/`connector`/`name`/`db` в `source` — константы для всего коннектора.

### 5.3 Компрессия и батчинг: подбор `linger.ms`

`zstd` жмёт **батч**, а не отдельное сообщение. Без `linger.ms` producer
отправляет батчи по мере готовности, они мелкие, и компрессия работает
вполсилы. Замерено:

| `linger.ms` | Б/сообщение на диске | сжатие | событий/с |
|---:|---:|---:|---:|
| 0 | 18,9 | 3,8x | 74 683 |
| **50** | **10,4** | **6,8x** | 77 459 |
| 200 | 10,3 | 6,9x | 83 822 |

**На чём остановились: `linger.ms = 50`.** Обоснование по цифрам:

- переход с 0 на 50 — это **в 1,8 раза меньше диска и трафика** (18,9 → 10,4
  Б/сообщение) при том же наборе событий. Это самая дешёвая оптимизация во всём
  проекте: одна строка конфига;
- переход с 50 на 200 даёт ещё 1% объёма (10,4 → 10,3) и добавляет до 150 мс к
  задержке доставки каждого события. За 1% платить задержкой не стоит:
  задержка складывается с лагом consumer'а части 2;
- рост скорости при 200 (83 822 против 77 459) в пределах разброса между
  прогонами — см. 5.4, где одна и та же конфигурация давала от 56 до 87 тысяч
  событий/с.

Остальные настройки батчинга: `batch.size = 262144` (256 КБ),
`compression.type = zstd`. На топике `compression.type=producer`, то есть
брокер не перепаковывает батчи — иначе экономия producer'а терялась бы.

### 5.4 Пропускная способность одной партиции

| конфигурация | событий/с (прогоны) |
|---|---|
| `slim`, `max.in.flight=5` | 56 497 · 67 889 · 71 942 |
| `slim`, `max.in.flight=1` | 84 104 · 84 531 · 87 413 |
| `full`, `max.in.flight=5` | 74 627 · 75 472 |

**Про `max.in.flight=1` против `5`.** Разница в гарантиях порядка между 1 и 5
при `enable.idempotence=true` **отсутствует** (механика — в разделе 6 и в
`CLAUDE.md`), поэтому вопрос был только в пропускной способности. Замер
показал, что **единица не медленнее**: наоборот, её прогоны легли выше. Скорее
всего это не свойство единицы, а разброс на коротком окне замера (1,1–1,8 с на
100 тысяч событий), но вывод от этого не меняется:

> **Запаса по суточному объёму хватает и на `max.in.flight=1`, значит единица
> приемлема как более консервативный вариант.** Она не «безопаснее» — гарантии
> те же — но и не дороже. Значение в `.env` (`MAX_IN_FLIGHT=5`) можно понизить
> до 1 без потери пропускной способности, если так спокойнее при ревью.

Чего делать нельзя ни при каком значении: убрать `enable.idempotence`, оставив
`max.in.flight > 1`. Это тихая поломка порядка.

### 5.5 Экстраполяция на сутки и вывод о применимости

По самому консервативному измеренному числу для профиля `slim`
(**56 500 событий/с**):

| | значение |
|---|---|
| пропускная способность одной партиции | ~56 500 событий/с |
| за сутки | **~4,9 млрд событий** |
| объём на диске за сутки (`slim`) | ~47 ГБ |
| то же на профиле `full` | ~137 ГБ |

По лучшему измеренному (84 100 событий/с) — 7,3 млрд событий и 71 ГБ в сутки.

**Вывод о применимости архитектуры.** Одна партиция — это потолок, который
нельзя поднять, не сломав инвариант №1. Замеренный потолок:

- **~4,9 млрд изменений в сутки** в самом консервативном сценарии;
- поток в 100 млн изменений в сутки (крупная банковская АБС) — это
  **~1160 событий/с**, то есть **2% измеренной пропускной способности**;
- поток в 1 млрд изменений в сутки — ~11 600 событий/с, **20% потолка**.

Значит **одна партиция не является узким местом** для реалистичного объёма, и
инвариант №1 не приходится размениваться на производительность. Узким местом
раньше станет применение в MS SQL (часть 2): одна транзакция на пачку,
блокировки в приёмнике, скорость дисков — это на порядок медленнее, чем
чтение из Kafka.

**Если фактический суточный объём в (А) окажется выше 4–7 млрд событий**, то
архитектура с одной партицией не подходит, и это **не настраивается**:
единственный путь — отказ от инварианта №1 (несколько топиков по группам
таблиц, не связанных внешними ключами) и переделка применения в (Б).
См. раздел 6.1.

### 5.6 Оговорки к цифрам

1. Замер сделан на **одном хосте**: брокер, три PostgreSQL и Connect в
   контейнерах на 8 ГБ RAM, arm64. Это **нижняя оценка**; на выделенном
   кластере числа будут выше, порядок — тот же.
2. Нагрузка — INSERT в одну таблицу (`sales.order_items`). Реальный поток из
   500 таблиц даст больше разных Avro-схем, больше промахов кэша схем и
   несколько худшую компрессию: однотипные сообщения жмутся лучше.
3. Окно замера короткое (1–2 с на 100 тысяч событий), отсюда разброс между
   прогонами до 1,5 раза. Для решения о применимости этого достаточно —
   разница между 56 тысячами и 87 тысячами событий/с не меняет вывода, —
   но для тонкой настройки надо мерить на своём контуре и на своих данных.
4. Компрессия измерена на приросте размера партиции, то есть включает
   накладные расходы Kafka на батчи и индексы, а не только полезную нагрузку.

### 5.7 Что оптимизировано

| приём | эффект |
|---|---|
| профиль `slim` (`ExtractNewRecordState`) | в 2,7 раза меньше трафика |
| `zstd` + `linger.ms=50` + `batch.size=256K` | в 1,8 раза меньше диска, чем без батчинга |
| `REPLICA IDENTITY DEFAULT` (только PK) | не пишет старый образ строки в WAL |
| `column.exclude.list` | тяжёлая колонка `catalog.products.spec_blob` не уезжает в Kafka — видно прямо в схеме: `contracts/examples/slim/catalog.products.Value.avsc` её не содержит |
| `tombstones.on.delete=false` + `drop.tombstones=true` | DELETE даёт одно сообщение, а не два |
| `publish = 'insert, update, delete'` | нет событий truncate |

Про `column.exclude.list` важная деталь: он режет **сообщение**, но **не
режет WAL** — колонка всё равно приходит от `pgoutput` и отбрасывается
коннектором. Чтобы не отдавать её и на стороне БД, нужна публикация со списком
колонок (PostgreSQL 15+):

```sql
ALTER PUBLICATION dbz_cdc_pub SET TABLE catalog.products (id, sku, name, supplier_id, currency_code, price, updated_at);
```

Это дало бы дополнительную экономию на стороне сервера, но **совместимость
публикаций с column list и Debezium 2.6 требует отдельной проверки**: коннектор
строит схему по каталогу таблицы, а не по составу публикации. На этом стенде
такой вариант не проверялся — сознательно оставлен как отдельная задача.

### 5.8 Что сознательно НЕ оптимизировано

**`decimal.handling.mode` оставлен `precise`.** Переключение на `double`
уменьшило бы сообщение (8 байт против ~10–12 у `bytes` + накладные расходы
схемы) и **молча испортило бы денежные значения**: `double` не представляет
десятичные дроби точно, ошибки накапливаются при суммировании, а обнаружатся
при сверке остатков. Это банковские данные — здесь размен неприемлем.

Цена решения известна и принята: `numeric` едет как Avro `bytes` +
`logicalType: decimal`, consumer части 2 обязан разбирать unscaled value со
scale из схемы. Плюс побочный эффект: `kcat -s value=avro -J` на таком потоке
обрывается (раздел 8).

**`time.precision.mode` оставлен дефолтным.** Уменьшение точности времени
экономит единицы байт и ломает сопоставление событий по времени.

**`__lsn` и `__txId` не убраны.** На них держатся порядок и идемпотентность
consumer'а: без `__lsn` невозможна дедупликация при рестарте, без `__txId` —
проверка полноты транзакции. Экономия 16 байт не стоит потери exactly-once.

## 6. Ограничения архитектуры

Это не недостатки реализации, а свойства принятых решений. Каждое стоит знать
до согласования, а не после.

### 6.1 Одна партиция — потолок без пути к масштабированию

Пропускная способность одной партиции — единственный предел всего пайплайна, и
**поднять его нельзя, не сломав инвариант №1**:

- добавить партиции в `cdc.events` — Kafka гарантирует порядок только внутри
  партиции, порядок между партициями не определён. Изменения одной таблицы (и
  тем более связанных таблиц) разъедутся по партициям, и consumer снова будет
  вынужден разбирать foreign key;
- поднять `tasks.max` — логический слот читается одним подписчиком; больше
  задач не даст ни скорости, ни корректности;
- параллелить consumer — второй участник consumer group просто не получит
  партицию.

Операция необратима: увеличить число партиций можно, уменьшить нельзя. То есть
ошибочное «расширение» топика лечится только пересозданием топика и новой
синхронизацией (Б).

Единственный корректный путь горизонтального масштабирования — **отказ от
инварианта №1**: несколько топиков (например, по группам таблиц, не связанных
внешними ключами), и тогда consumer обязан уметь применять их независимо.
Это другая архитектура и другой объём работы в части 2.

Замеренный потолок и вывод о применимости — раздел 5.

### 6.2 CDC зависит от здоровья реплик

`synchronized_standby_slots = 'replica_1_slot,replica_2_slot'` заставляет
мастер придерживать walsender'ы логического слота, пока обе реплики не
подтвердят приём WAL. Следствия:

- отстала реплика — **притормозил поток CDC**;
- упала реплика и её слот остался неподтверждённым — поток CDC остановится;
- при этом WAL продолжает удерживаться слотом, то есть **растёт диск на
  мастере**.

Это осознанный размен: целостность при failover в обмен на независимость от
здоровья standby. Практический вывод для эксплуатации: **лаг реплик надо
мониторить как часть здоровья CDC**, а не отдельно. Если реплику выводят из
эксплуатации надолго, её слот надо убрать из `synchronized_standby_slots`
(и обратно — при возврате).

### 6.3 CDC читается только с мастера

С синхронизированного слота на реплике читать нельзя до промоушена — это
запрет самого PostgreSQL, а не настройка:

```
ERROR:  cannot use replication slot "dbz_cdc_slot" for logical decoding
DETAIL: This replication slot is being synchronized from the primary server.
```

Значит нагрузку логического декодирования (а это CPU на мастере) **нельзя
перенести на реплику**. Реплики в этой схеме служат только для failover и для
читающих запросов, не связанных с CDC.

### 6.4 Запрет на создание слотов не обеспечивается правами

Подробно — раздел 2.7. Кратко: роль с атрибутом `REPLICATION` может создать
слот по репликационному протоколу, а Debezium 2.6 создаёт отсутствующий слот
сам, причём **без `failover`**. Значит ограничение «Debezium не создаёт слоты»
существует как договорённость и как контроль состояния, но не как техническая
гарантия. Нужен алерт на логические слоты с `failover = false`.

### 6.5 Профиль `slim` необратимо теряет часть информации

`before`-образ, события `truncate` и `message`, часть диагностики из блока
`source` — их нет в потоке и восстановить их из топика нельзя. Если позже
понадобится before-образ (например, для аудита изменений в (Б)), придётся
переключиться на профиль `full` и **пересинхронизировать** (Б), потому что
старые сообщения уже записаны в формате `slim`.

### 6.6 Один heartbeat-топик на коннектор, retention как жёсткий срок

Retention `cdc.events` (на стенде 7 суток) — это окно, за которое consumer
части 2 **обязан** успеть. Простой consumer'а дольше retention означает не
задержку, а потерю данных и повторную синхронизацию (Б). Это надо
мониторить: и лаг consumer'а, и лаг слота.

## 7. Что дальше

Часть 2: Kafka → MS SQL (Б) через собственный consumer.

Что уже готово в этом репозитории как задел:

- **контракт потока** — `contracts/` (эталонные схемы руками + полная выгрузка
  из Schema Registry, `make contracts`);
- **требования к consumer'у** — раздел 4 этого файла: один читатель, разбор по
  id схемы, `MERGE` по PK, `last_lsn` в той же транзакции, ручной коммит
  offset'а после коммита БД, реакция на новую версию схемы;
- **MS SQL** поднимается в профиле `sink` (`make up-sink`), в части 1 не
  используется;
- **топик и его гарантии** проверены: `make verify` и `make verify-infra`
  запускаются на каждый прогон и падают на нарушении.

Что предстоит решить в части 2 и чего этот стенд не решает:

1. **Схема (Б).** Соответствие типов PostgreSQL → MS SQL, в первую очередь
   `numeric(p,s)` → `decimal(p,s)` (Avro `bytes` + `logicalType: decimal`,
   разбирать через unscaled value + scale) и `timestamptz` →
   `datetimeoffset`/`datetime2`.
2. **Стратегия применения.** `MERGE` по PK — самый простой корректный вариант,
   но на больших пачках он дороже раздельных INSERT/UPDATE. Мерить на своих
   объёмах.
3. **Мониторинг.** Лаг consumer'а по offset'ам, лаг применения по
   `__ts_ms`, лаг слота на мастере, число ошибок применения.
4. **Реакция на изменение схемы.** Что делать автоматически (добавленная
   nullable-колонка), а что останавливать (удалённая колонка, смена типа).
5. **Второй контур.** Если понадобится больше пропускной способности, чем даёт
   одна партиция, — см. раздел 6.1: это отказ от инварианта №1 и переделка
   применения в (Б).

## 8. Troubleshooting

### Слот отсутствует или занят

```
ERROR: replication slot "dbz_cdc_slot" does not exist
```

Слота нет. **Важно:** Debezium 2.6 в этом случае **создаст его сам** и
стартует, а созданный им слот будет **без `failover`** (см. раздел 2.7).
Поэтому ошибку выше вы увидите редко; чаще проблема обнаружится так:

```sql
SELECT slot_name, failover, synced FROM pg_replication_slots WHERE slot_type='logical';
```

Если у рабочего слота `failover = f` — слот создан не тем способом. Лечение:
остановить коннектор, дропнуть слот, создать заново правильным SQL
(раздел 2.4) и синхронизировать (Б) заново — позиция потеряна. То есть
`make reset-cdc` плюс внешняя синхронизация.

```
ERROR: replication slot "dbz_cdc_slot" is active for PID 1234
```

Слот занят: либо работает второй коннектор с тем же `slot.name`, либо
предыдущая задача не отпустила соединение.

```sql
SELECT slot_name, active, active_pid FROM pg_replication_slots;
SELECT pid, application_name, backend_start, state FROM pg_stat_activity WHERE pid = <active_pid>;
```

Зависшее соединение — `SELECT pg_terminate_backend(<active_pid>);`. Второй
коннектор — у каждого коннектора должен быть **свой** слот (как у профиля
`full`: `dbz_cdc_slot_full`).

### Коннектор в FAILED

```bash
make connector-status
```

```bash
docker compose logs connect --tail=200
```

| в трейсе | причина | лечение |
|---|---|---|
| `publication "dbz_cdc_pub" does not exist` | публикации нет, а `publication.autocreate.mode=disabled` | создать публикацию SQL-скриптом (раздел 2.5) |
| `permission denied for database` | попытка создать публикацию под ролью `debezium` | не автосоздание, а SQL: у роли нет и не должно быть CREATE |
| `no pg_hba.conf entry for replication connection` | нет строки `host replication debezium ...` | раздел 2.7 и `pg/master/pg_hba.conf` |
| `Topic ... not present in metadata` | топика нет, auto-create выключен | `make topics` |
| `NoSuchMethodError` / `NoClassDefFoundError` в конвертере | версия `kafka-connect-avro-converter` не из линейки CP | раздел 9, блокирующее расхождение |
| `OutOfOrderSequenceException` | это **не ошибка конфигурации**: идемпотентный producer отверг батч, пришедший не по порядку, и перестроит очередь | ничего; если повторяется постоянно — смотреть сеть и стабильность брокера |

Перезапуск задачи без переустановки коннектора: `make connector-restart`.

### Schema Registry отвергает схему

```
Schema being registered is incompatible with an earlier schema for subject "cdc.events-value"
```

Ключевая улика — **subject называется `cdc.events-value`**. Значит работает
дефолтная `TopicNameStrategy` и схемы всех таблиц пишутся в один subject.
Лечение — вернуть в конфиг:

```json
"key.converter.key.subject.name.strategy": "io.confluent.kafka.serializers.subject.TopicRecordNameStrategy",
"value.converter.value.subject.name.strategy": "io.confluent.kafka.serializers.subject.TopicRecordNameStrategy"
```

Правильные subject'ы выглядят как `cdc.events-dbz.catalog.products.Value`.
Проверить: `curl -s http://localhost:8081/subjects | jq`.

Если subject правильный, а совместимость всё равно нарушена — структура
таблицы изменилась несовместимо (удалена колонка, изменён тип). Это сигнал
человеку, а не повод понижать `compatibility`.

### События ушли в другой топик

Симптом: в `cdc.events` пусто, зато появились топики `dbz.catalog.products` и
подобные. Либо наоборот — в `cdc.events` приехали heartbeat и метаданные
транзакций.

Причина в регекспе роутера. Правильно:

```json
"transforms.reroute.regex": "^dbz\\.[^.]+\\.[^.]+$"
```

**Ровно три сегмента.** `^dbz\..*` захватит `dbz.transaction` (2 сегмента), а
`^dbz\.[^.]+$` не захватит ни одной таблицы. Проверить фактический конфиг:

```bash
docker compose exec -T connect curl -s http://localhost:8083/connectors/pg-cdc/config | jq '."transforms.reroute.regex"'
```

Второй вариант той же проблемы — перепутанный порядок трансформаций. Должно
быть `"transforms": "unwrap,reroute"`, именно в этом порядке.

### Сервис не стартует из-за отсутствующего топика

Так и задумано: auto-create выключен, отсутствующий топик роняет сервис, а не
появляется сам с дефолтной политикой очистки.

```
org.apache.kafka.common.errors.UnknownTopicOrPartitionException
```

Лечение: `make topics` — идемпотентно досоздаёт всё из списка.

Если воркер жалуется на **число партиций** служебного топика — оно должно
совпадать с `CONNECT_OFFSET_STORAGE_PARTITIONS=25` и
`CONNECT_STATUS_STORAGE_PARTITIONS=5`. Уменьшить число партиций нельзя, только
пересоздать топик.

### WAL растёт

```sql
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS not_read
FROM pg_replication_slots ORDER BY 2;
```

Причины по частоте:

1. **Коннектор стоит** (`active = f`) — слот держит WAL, и это правильно, но
   надолго так оставлять нельзя. Поднять коннектор.
2. **Нет heartbeat.** Если по отслеживаемым таблицам затишье, а в базе идёт
   другой трафик, подтверждённый LSN не двигается. Проверить
   `heartbeat.interval.ms` в фактическом конфиге и наличие сообщений в
   `__debezium-heartbeat.dbz`.
3. **Отстала реплика.** `synchronized_standby_slots` заставляет мастер
   придерживать walsender'ы (раздел 6.2):

   ```sql
   SELECT application_name, state, replay_lag FROM pg_stat_replication;
   ```
4. **Consumer части 2 не читает** — на WAL не влияет напрямую, но влияет на
   retention топика.

Чего **не** делать в панике: ставить `max_slot_wal_keep_size`. При превышении
Postgres инвалидирует слот, а это полная пересинхронизация CDC. Сначала
разобраться, почему не двигается позиция.

### Кончился кэш схем

Симптом: плавающие ошибки сериализации под нагрузкой, рост числа запросов к
Schema Registry, иногда таймауты. 500 таблиц x (ключ + значение) ~ 1000 схем
при дефолтном `max.schemas.per.subject = 1000` — ровно на границе.

```json
"key.converter.max.schemas.per.subject": "5000",
"value.converter.max.schemas.per.subject": "5000"
```

Сколько схем зарегистрировано:

```bash
curl -s http://localhost:8081/subjects | jq 'length'
```

### Consumer не может прочитать топик: «Schema N not found»

```
{"error_code":40403,"message":"Schema 20 not found"}
```

Схему удалили из Schema Registry, а сообщения с её id остались в топике.
Типичный сценарий: таблицу вывели из CDC и «убрали за собой» лишний subject.

**Восстановить нельзя.** Повторная регистрация той же схемы даёт НОВЫЙ id, а в
сообщениях записан старый. Единственное лечение — пересоздать топик
(`make reset-cdc`) и синхронизировать (Б) заново, то есть заплатить полную
цену за уборку.

Правило: **не удалять subject'ы, пока в топике есть сообщения этого id** —
как минимум до истечения retention (на `cdc.events` это 7 суток). Ненужные
схемы просто оставляют лежать, они ничего не стоят и никому не мешают.

Проверить, что id ещё жив:

```bash
curl -s http://localhost:8081/schemas/ids/20 | jq
```

### Реплика не синхронизирует слот

`synced = f` или слота на реплике нет вовсе. Проверять по порядку:

1. `sync_replication_slots = on` на реплике;
2. `hot_standby_feedback = on` на реплике;
3. `primary_slot_name` задан и слот существует на мастере;
4. **`dbname` есть в `primary_conninfo`** — самая частая причина, без него
   slotsync-воркер молча не работает:

   ```sql
   SELECT setting FROM pg_settings WHERE name = 'primary_conninfo';
   ```
5. у слота на мастере `failover = t` — без флага синхронизировать нечего;
6. в логе реплики искать `slotsync`:

   ```bash
   docker compose logs pg-replica-1 | grep -i slotsync
   ```

### kcat читает не весь топик и молчит об этом

```
% ERROR: Failed to deserialize value in message in cdc.events [0] at offset 18:
  Error parsing JSON: <NUL> is not allowed without JSON_ALLOW_NUL
```

Штатная команда `kcat -s value=avro -r ... -J` **обрывается на первом же
сообщении с Avro-полем `bytes`**, а это все денежные поля:
`decimal.handling.mode=precise` кодирует `numeric` как `bytes`, и конвертер
Avro в JSON внутри libserdes не умеет представлять нулевой байт. Опаснее всего
то, что уже прочитанное выглядит как полный поток — на этом стенде так
получалось 18 сообщений из 53.

Лечение: читать поток через `kafka-avro-console-consumer` (он использует Avro
`JsonEncoder` и кодирует `bytes` escape-последовательностями) — так делает
`scripts/verify-order.sh`. `kcat` остаётся полезен там, где десериализация не
нужна: размеры сообщений (`-f '%S %K'`), таймстемпы (`%T`), счёт, ручной
просмотр сырых записей.

И **не** переключайте `decimal.handling.mode` на `double`, чтобы «починить
kcat»: это молча испортит денежные значения.

### kafka-avro-console-consumer печатает свой конфиг вместо данных

Он пишет log4j **в stdout**, а не в stderr, поэтому `2>/dev/null` не
помогает — десятки строк `INFO ConsumerConfig values:` попадают в разбираемый
вывод. Нужен фильтр строк данных: они начинаются с `{` или с `Partition:`.
В `scripts/lib.sh` для этого есть функция `avro_consume`.

### Что делать с этим списком

1. **Сначала avro-converter.** Это единственное блокирующее расхождение: с

2. **Потом Debezium 2.6.2.** Дешёвый апгрейд, закрывает потерю событий при
   рестарте — то есть прямой риск для целостности (Б).
3. **Параллельно выяснить, что такое Schema Registry «v1.17.1».** От ответа
   зависит, работает ли выбранная subject naming strategy, а на ней держится
   единый топик.
4. **Нагрузочный тест PG 17 + Debezium 2.6** на реальном объёме — до
   продуктива. Стенд показывает, что связка функционально работает; он не
   показывает, как она ведёт себя на 500 таблицах и суточном потоке.
